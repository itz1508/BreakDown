BreakDown v6 workflow

Seven workflow stages, four processing-plan handoffs. The diagram describes the declarative contract; runtime enforcement is a separate implementation concern.

01

audit_pre_research

AUDITOR · PP1
Preserve the request, inspect repository scaffolding read-only, prepare research items and source checkpoint. Runtime creates PP1; Auditor creates PP2.
02

gate_1

USER · DECISION
Confirm or cancel the exact PP2 handoff before Research. The decision is not a processing-plan input.
03

research

RESEARCHER · PP2
Investigate questions, preserve source citations, generate evidence-backed fixtures where possible, and retain resolved and unresolved questions.
04

audit_post_research

AUDITOR · CODER SUB-ROLE
Reconcile research with source, normalize findings and coding inputs, then create PP3. This stage does not execute PP3.
05

planning

PLANNER · PP3 → PP4
Resolve gaps, perform scan/verify/chaos self-review, produce the strict requirement specification, freeze and hash it, run preflight and obtain user confirmation. Runtime creates PP4 after confirmation.
06

builder

BUILDER · PP4
Verify hashes, enter the sandbox, execute implementation_steps sequentially using apply → check → record, synchronize eligible results and exit.
07

completion

RUNTIME · TERMINAL RECORD
Record the actual outcome, changed files, checks performed, success-criterion results, partial work, retained evidence and remaining tasks.

Processing-plan ownership

PP1 Runtime → Auditor · PP2 Auditor → Researcher · PP3 Auditor → Planner · PP4 Planner → Builder. Plan definitions and runtime records use separate schemas.

Execution boundary

Builder is sequential. Stop on the first not_valid task. Partial results remain evidence and are not synchronized to application source unless all tasks complete within approved scope.

Planning's scan/verify/chaos work is self-review, not an independent-verification stage. This visualization is declarative and does not claim that the v6 workflow runtime is installed.
